# 根因说明：`input/tool.py` 为什么会「不报错、结构完整、结果全错」

行号均指**修改前**的 `input/tool.py`（共 63 行）。结论先给：这不是一个 bug，而是三处缺陷叠在一起，
分别发生在**编码层 → 切分层 → 错误处理层**；其中「错误处理层」把前两层的错误全部吞掉，
所以进程正常退出、`out/summary.json` 结构完整，只是数字是错的。

实测对照（同一份 `input/ledger.csv`，350 字节，UTF-8、LF、无 BOM）：

| 指标 | 原脚本 | 正确值 |
| --- | --- | --- |
| `rows_total` | 11 | **14** |
| `amount_total` | 315300 | **909300** |
| 品类键 | `'\u947c\u8dfa\u5f7e'`、`'\u935c\u6827\u668b\u749e\ufffd'` …（乱码，含 U+FFFD） | 茶叶 / 咖啡豆 / 礼盒,精品 / 陶瓷杯 |

丢掉的正好是 3 条带引号且引号内含逗号的记录：`ledger.csv` 第 3 行 S-03、第 7 行 S-07、第 15 行 S-13
（都是 `"礼盒,精品"`）；丢失金额 158000 + 316000 + 120000 = **594000** = 909300 − 315300，与差额完全吻合。

---

## 缺陷 1（编码层）：第 21 行 —— 用 GBK 解 UTF-8，还用 `replace` 把解码错误抹平

```python
21:    text = data.decode("gbk", errors="replace")
```

**机制**：文件是 UTF-8，脚本按 GBK 解。GBK 和 UTF-8 都是变长多字节编码，UTF-8 的字节序列
在 GBK 里往往"碰巧"也能凑成合法的双字节字符，所以 `decode` 不抛异常，而是给出**另一串字符**——
这就是品类名乱码的直接原因（`茶叶` 变成 `'\u947c\u8dfa\u5f7e'` 之类）。

更糟的是 `errors="replace"`：GBK 里凑不成的字节被替换成 `U+FFFD`（`\ufffd`），
**解码错误被降级成"数据里的一个字符"**，于是连"文件根本不是 GBK"这个唯一可能报警的信号也没了。
实测这文件用 `errors="strict"` 解 GBK 会立刻 `UnicodeDecodeError: 'gbk' codec can't decode byte 0x86 in position 33`，
即"严格解"本来能当场报错——是 `errors="replace"` 把它吞掉的。

**连带风险**（本文件未触发，但同一行导致）：`U+FFFD` 若落进 `qty`/`unit_cents` 字段，`int()` 就会失败，
再被缺陷 3 的 `continue` 静默丢行；两个不同品类也可能被解成同一个乱码键而被**静默合并**，反之亦然。

**改法**：`text = data.decode("utf-8-sig")`（容忍 BOM），并把 `UnicodeDecodeError` 显式转成
`ValueError`——解码失败必须炸出来，不能替换成"看起来像数据"的字符。

---

## 缺陷 2（切分层）：第 26 行 —— 裸 `split(",")` 不认识引号，还把每个字段都 `strip()`

```python
26:        parts = [p.strip() for p in line.split(",")]
```

**机制**：任务书规定字段可被半角双引号包裹、包裹内的逗号属于字段内容。
`"礼盒,精品"` 用 `split(",")` 会被切成两段 `"礼盒` 和 `精品"`，
于是 `S-03,"礼盒,精品",1,158000` 得到 **5** 个元素：
`['S-03', '"礼盒', '精品"', '1', '158000']`。
这既不是 4 个字段、`parts[2]` 也不是数字——错误在这一层已经发生，但此刻**还没有丢数据**，
只是"一行被读歪了"；真正把它变成"数据消失"的是下一处缺陷。

同一行的 `p.strip()` 还有第二个问题：它对**所有**字段无差别去空白，包括被引号包裹的字段，
会把引号内本来有意义的首尾空格一起吃掉（本文件数据没触发，但属于同一处的语义错误）。

**改法**：按 CSV 引号规则切分——引号必须紧贴字段边界、成对闭合，`""` 表示一个字面引号，
右引号之后只允许空白；只对**未被引号包裹**的字段做 `strip()`。
修好的 `tool.py` 里对应 `_split_line()` + `_field_text()`（等价地也可以直接用标准库 `csv.reader`）。

---

## 缺陷 3（错误处理层，数据真正被吞掉的地方）：第 27–33 行 —— `except Exception: continue`

```python
27:        try:
28:            store = parts[0]
29:            category = parts[1]
30:            qty = int(parts[2])
31:            unit_cents = int(parts[3])
32:        except Exception:
33:            continue
```

**机制**：缺陷 2 把 `"礼盒,精品"` 那一行切歪后，第 31 行 `int('精品"')` 抛 `ValueError`，
第 32 行的 `except Exception` 原样接住，第 33 行 `continue` 跳过整行——**整条记录消失，且不留任何痕迹**。
`S-03`、`S-07`、`S-13` 三条就是这样没的，`rows_total` 由 14 掉到 11。

这层错误的本质是**把"输入不合法"和"程序有 bug"用同一个兜底吞掉**：
`except Exception` 同时接住 `IndexError`（字段不足，例如 `S-01,a,2`）、`ValueError`（数字不合法）、
`TypeError` 等等，一律 `continue`。于是：
- 进程退出码仍是 0；
- `out/summary.json` 字段齐全、能正常 `json.load`；
- 少掉的记录没有任何输出、没有计数、没有日志；
- 结果"看起来对"，所以能一路活到生产。

**改法**：删掉 `try/except ... continue`，改为显式校验并 `raise ValueError("第 N 行：…")`，
让字段数不对、数字不合法、引号未闭合、不是 UTF-8 这四类问题都在调用处直接抛出；
错误信息带上物理行号，便于定位。

---

## 缺陷 4（校验缺失）：第 30–31 行 —— `int()` 不等于「十进制整数」

```python
30:            qty = int(parts[2])
31:            unit_cents = int(parts[3])
```

**机制**：Python 的 `int()` 比"十进制整数"宽：`int("1_000") == 1000`（下划线分隔）、
`int("+5")`、`int(" 5 ")`、`int("٤")`（非 ASCII 数字）都能通过。
本文件里 qty/unit 都是规范十进制，**这处没有直接造成本次 3 行丢失**（直接原因是缺陷 2 + 3），
但它让"值不合法"这条路径更难被发现——而且一旦发生，就会被第 32 行静默吞掉。

**改法**：先按 `^[+-]?[0-9]+$` 校验再 `int()`，不匹配即 `ValueError`（见 `_to_int()`）。

---

## 缺陷 5（可维护性，非数据错误）：第 47–49 行 —— `amount_total` 用第二个循环重算

```python
47:    amount_total = 0
48:    for row in rows:
49:        amount_total += row["qty"] * row["unit_cents"]
```

**机制**：`by_category[*]["amount"]` 在第 43–46 行累计，`amount_total` 在第 47–49 行又独立算一遍，
两个口径不共享同一处累加。当前结果一致，但任何只改一处的维护都会让"总额 ≠ 各品类之和"，
而由于没有自检，这类不一致同样不会报错——和本次事故是同一种失效模式。
另外它说明 `summarize` 是"忠实汇总"的：11 行就汇总出 11 行，问题在 `parse_bytes`，不在聚合。

**改法**：在同一个循环里累加 `rows_total` / `amount_total`，并在 `main()` 里用断言对账
（明细行数之和 == `rows_total`、各品类金额之和 == `amount_total`），一旦不自洽立即失败。

---

## 缺陷 6（可观测性）：第 55 行 —— `main()` 只写文件，不报数、不对账

```python
55:    summary = summarize(parse_bytes(LEDGER.read_bytes()))
```

**机制**：`main()` 既不打印解析出的记录数，也不拿它和文件的记录行数对账，
所以"14 行进、11 行出"这件事在运行时完全不可见。
**改法**：`main()` 打印 `rows_total` / `amount_total` / 品类数，并保留上面的自检断言。

---

## 顺带核对：不是缺陷的地方

- 第 22–25 行：`splitlines()` 能正确处理 LF/CRLF，`strip()` 后判空行与 `#` 前缀，逻辑正确。
- 第 43–46 行：用 `setdefault` 按 `category` 聚合 `rows/qty/amount`，逻辑正确（键被污染是缺陷 1 造成的）。
- 第 57 行：`ensure_ascii=False` + `indent=2` + `sort_keys=True`，只是输出格式，与正确性无关。
- 第 61–63 行：`main()` 走 `__name__` 守卫，没问题。

## 修好后自检（`python tool.py` 实跑结果）

- 逐品类：
